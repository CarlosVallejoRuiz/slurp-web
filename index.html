// the problem

Your LLM doesn't need the whole bowl

slurp index maps your entire codebase into a knowledge graph using pure static analysis — no LLMs, no APIs. But injecting every node into every query is wasteful — your LLM spends most of its context budget on nodes it'll never use.

slurp scores each node against your query — TF-IDF over its name, file path and scope, plus a PageRank personalised on the query — with zero LLM calls and zero extra tokens spent, and serves only what fits inside your budget.

The v1.4 ranking

v1.4.0 changes the order in which slurp ranks nodes, so the same budget holds more of what a question needs. The semantic score reads the terms of a node's file path and of the class or module that holds it, at the weight of its name; the structural score is a PageRank personalised on the query. It was chosen on a bank of 1,525 questions taken from the commit history of 14 open-source projects — a commit's subject as the question, the definitions it changed as the answer — compared on 7 projects and then checked once on the other 6. What gets worse: in JSON at 4000, PrismaStats falls from 0.900 to 0.867 (the equivalent of half a question) and slurp from 0.812 to 0.750 (one question); in markdown at 16000, slurp falls from 1.000 to 0.938 (one question). Choosing a budget

A study with slurp v1.3.0, on the same 1,525 questions from the commit history of 14 open-source projects, looked for the budget past which more tokens find nothing new. For pinning down the specific function a change touches, it found none: recall keeps growing, about 10 points per doubling, up to 32000 with no plateau, in projects with more than about 2,000 candidate nodes (those slurp may return: no tests, no imports). There, in markdown and with v1.3.0, 4000 finds 34–68% of the changed definitions, 16000 finds 52–75% and 32000 finds 59–81%.

So the default stays 4000 — doubling the context for ten points is a trade-off, not an optimum — and what v1.4 improved is the ranking. As a guide: for architecture questions, the default is enough; for pinning down one specific function in a large project, pass 16000–32000. slurp_query's description tells the agent the same.

v1.1.0 is about 1.5 ms slower per query than v0.7.0, and does more for it: the budget costs relationships as well as nodes, and the text is rendered and counted before it is sent.

v1.4.0 against v1.3

Measured with another method than the table above, so the figures cannot be compared with it: six reference graphs, v1.4.0 beside v1.3 in the same session, with the encoder loaded. Warm queries (the median of 20) take 0.31–0.71× v1.3's time on hono, slurp, tokio, prometheus and sqlalchemy (sqlalchemy, 59,518 nodes: 278 → 87 ms); on PrismaStats, the smallest, they are slower: 10.2 → 14.4 ms. The first query on a freshly loaded graph is slower too, up to 1.54× (hono: 41.9 → 64.4 ms): the new ranking builds once per graph the terms of every name and path, which is what makes every later query faster. The release criterion allowed 1.5× on that first query; the author's rule, fixed before measuring again, accepts up to 1.67× on it alone. The first slurp_query after the MCP server refreshes the graph takes 1.03–1.45× v1.3's.

// how it works

From zero to optimized in minutes.

0

New to slurp?recommended

With slurp installed (step 1), run slurp init in your project root. It shows the whole plan and asks before writing anything: it builds a graph that keeps itself current, registers the MCP server in .mcp.json, approves it for Claude Code so the agent does not ask for approval, and tells your agent when to use slurp. Then restart your AI coding assistant — steps 2 and 3 are already done.

# guided one-command setup slurp init
1

Install slurp

One command. Requires Python 3.12+.

# install pip install slurp-graph
2

Index your project locallymanual setup

slurp index . analyzes your code with pure static analysis — no LLMs, no APIs, no cost.

# generates the graph locally slurp index . # Output on PrismaStats: 1582 nodes · 1852 edges · 185 files

ℹThe graph keeps itself current: before every answer — each MCP call and the query commands in the terminal — slurp checks the working tree (0.4 ms per call on PrismaStats) and refreshes its own graph if a file changed: 30 ms for an edit inside function bodies, 0.29 s for a full index, on PrismaStats. A call waits at most 2 seconds for a refresh.

ℹSo you no longer re-index by hand. slurp index . --watch is only needed for tools that read graph.json outside slurp, and no longer depends on watchdog; slurp index . --smart re-parses only the files that changed, with no git needed.

ℹWant to understand your codebase? slurp explain "functionName" explains any function in plain language.

ℹBefore editing a file, run slurp impact <file> to see what might break.

3

Configure MCP once, done forevermanual setup

Add slurp to your .mcp.json. Claude Code calls it automatically. Set up by hand, Claude Code asks once for the server and before each call unless you answer “don't ask again”; slurp init writes that approval for you.

Global install:

{ "mcpServers": { "slurp": { "command": "slurp", "args": ["serve", "--graph", "/absolute/path/to/graphify-out/graph.json"] } } }

Python project with uv:

{ "mcpServers": { "slurp": { "command": "uv", "args": ["run", "slurp", "serve", "--graph", "graphify-out/graph.json"] } } }
Fully automatic after slurp init. Claude Code calls slurp's tools when it needs them, without asking for approval, and the graph refreshes itself before each answer — no extra commands, no prompt engineering. You work exactly as before, just cheaper.

Already using graphify? slurp works with your existing graph.json out of the box, read-only: it never rebuilds or rewrites it, and answers say when files it covers changed after it was built. slurp init builds slurp's own graph beside it (graphify-out/slurp-graph.json), which auto-discovery picks first; slurp index asks before replacing graphify's (--force replaces it).

Measured with agents

Before the v1.3.0 release, ten claude -p sessions (Claude Code 2.1.331, Claude Opus 5.5) each did one task in a fresh clone set up with slurp init --yes — five on slurp itself, five on PrismaStats. No prompt mentioned slurp. Against a criterion fixed before measuring (8 of 10 sessions needed):

9/10 sessions called slurp on their own, all 9 before their first edit
0 approvals: no slurp tool was denied
10/10 tasks completed: the project's checks pass and the diff does what the task asked

Its limits

  • n = 10, from a single run, and the model varies from one run to the next.
  • The one session without slurp had a prompt that named both symbols to change and the component they live in. The agent grepped for them: with the names given, the task was finding them, not working out where the code lives, which is what slurp_query is for.
  • The refresh was barely exercised. Agents call slurp when they start, before editing: 15 of the 16 calls found the graph current and one refreshed it, in 325 ms.
  • Only 4 of the 26 files edited had a slurp_impact or slurp_explain first.

// features

Built different.

slurp explain

LLM-powered architecture explanations. What any function does, who calls it, and the risk of changing it. Works with Anthropic, OpenAI, Ollama, or any compatible endpoint.

slurp eval

Recall against labelled nodes with no LLM, no cost, reproducible (--retrieval). Or an LLM judge that scores answers with slurp context against the full graph.

slurp index --smart

Incremental re-indexing from a manifest in graph.json, no git needed. Produces the same graph as a full index, and is faster when only function bodies change.

slurp advisor

Recommends optimal token budget from your query history.

Multi-graph federation

Query multiple codebases simultaneously.

Call graph

Python, TypeScript/JS, Go, Java and Rust. Cross-file resolution for all five languages. Accurate blast radius analysis.

slurp impact

Pre-edit blast radius analysis. Know what breaks before you touch a file.

--suggest

Query recommendations from the graph frontier. Know what to explore next.

--viz

Compare graph snapshots
